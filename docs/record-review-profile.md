# DUFMech Structured Review Profile

All new reviews follow [record-reviews.md](record-reviews.md). The authoritative
artifact is `reviews/structured/<timestamp>-<slug>/review.yaml`; its sibling
`review.md` is derived by the shared saver. The eight skill routes declared in
`conf/record_review.yaml` cover native record, category/sample, repository and
curation audit-only requests in both agent frontends. The native skills have no
managed generic-template regions; their domain rubrics remain local.
The separate `review-open-issues` route ranks GitHub issues and does not perform
record review; scientific review discovered during triage uses these routes.

## Commands and Native Adapter

From this checkout's locked Python environment:

```bash
uv run --locked dufmech-review inspect record PF04149
uv run --locked dufmech-review inspect category seeds --members PF04149 PF19054 --selection 'Explicit two-family audit'
uv run --locked dufmech-review inspect repo review-code --scope-path src/dufmech/reviews.py
uv run --locked dufmech-review save --content /absolute/session/completed-review.yaml
just reviews-check
uv run --locked dufmech-review list --pfam-id PF04149
```

Inspection is read-only. It verifies the frozen worklist manifest and returns
native `context`, available `records`, rubric headings, and `structured` source
and target fields. Copy `structured.repository`, `kind`, `source`, and `targets`
into the common document. Add actual reviewer/independence, UTC start/finish,
scope/coverage, checks, evidence, assessments, findings/actions and limitations.
The old `context/sections` content envelope is no longer accepted for new saves.
Never infer a completed review from inspection or synthesize scientific findings
from source hashes. No provider or batch research call is part of this route.

Native `repo` inspection maps to common `kind: repository`. A category needs
explicit boundary decisions. A sampled selection can use `kind: batch`, retaining
the native category inspection's exact members and selection rule. Record the
population denominator, sample method, seed/strata, exclusions, and coverage.
Use common `inspect --input` when capturing additional schema, rubric or evidence
files; retain every native source input and snapshot ID. The native saver
recomputes snapshot/projection bindings, then delegates immutable persistence and
raw-input rechecks to `scripts/record_review.py`. Choose a new ID on collision.

The common validator also supports partial/blocked observations. Required checks
that could not run must remain unavailable; limitations explain the missing
coverage. Raw research output, source freezes, score tables and deterministic
knowledge-gap proposals remain inputs, not completed scientific reviews.

Every passing reviewed target needs a positive assessment linked to evidence;
checks alone and absence of findings cannot establish a pass. Plain `pass` may
not retain unknown or concerning assessments. Terminal findings require actual
review and assessment of their targets and nonfailed completion. Supersession
preserves each predecessor finding's targets, even for partial observations. Use the
common currentness/planning views to distinguish terminal from current findings.
Retained Git provenance must verify against historical input bytes; native
loading rejects unverifiable provenance. These are additional artifact gates,
not replacements for the native digest, history or scientific-evidence rules.

## Domains and Ownership

Read `docs/records.md`, `docs/reviews.md`, `docs/history.md`, `docs/sources.md`,
and `.claude/skills/curate-yaml-record/references/review-checklist.md`.
Retain the native questions in common assessments: exact Pfam/InterPro identity,
family versus tested protein scope, experimental/computational/contextual
evidence, quotation integrity, frozen provenance, completeness, contradictions,
and category lump/split reasoning. Assessment details retain domain prose;
dimensions can retain evidence tier, characterization state or protein/subfamily
scope with definitions and evidence references. Scores need a named scale and
denominator; seed/scoring status is not scientific review.

`data/families/PFxxxxx.yaml` is generated by `src/dufmech/records.py`; proposed
scientific fixes belong to `curation/families/PFxxxxx.yaml` and licensed evidence
extracts. Source identity/counters belong to verified `data/worklists/` snapshots
and their upstream freeze/derivation workflows. Do not edit those immutable
snapshots or generated Pages. For a row-only target, use the frozen JSON path and
separate exact `selector: pfam_id=PFxxxxx`; a row has no projection semantic digest.

## Verdicts and Status Gates

Preserve the native verdict separately:

| Native verdict | Common verdict |
| --- | --- |
| PASS | pass |
| SEED_ONLY | seed_only |
| NEEDS_FOLLOWUP | needs_curation, pass_with_limitations, or not_assessed |
| BLOCKED | blocked or not_assessed |
| FAIL | needs_curation |

The projection's `semantic_digest.algorithm` is `dufmech-record-content-v1`.
It uses the existing canonical JSON SHA-256, excluding only `curation_status`,
`review_id`, and the derived `curation_events` index. Claims, evidence,
`curation_history`, provenance and all other scientific content stay bound.

New `review_id` pointers use the canonical YAML path. To qualify `REVIEWED`,
the native reader requires a completed full-scope per-record common `pass`,
explicit native `PASS`, the exact Pfam projection digest, and an existing
canonical REVIEW history event with an allowed outcome, target, timestamp and
link to `review_report_url(review_id)`. Saving never creates history or promotes
a record. Historical Markdown remains loadable for existing references.

Preserve DUFMech's established distinction: a scoped PASS can be a non-scientific
audit. Its explicit `scientific_review` boolean remains separate from
`curation_status`; neither schema validity nor REVIEWED proves experimental
characterization. Deterministic checks must declare `scientific_review: false`.
Category, batch, repository, row-only, incomplete and non-PASS reviews cannot
promote a projection.

## Validation and Publication

`just reviews-check` runs the common profile/bundle/roundtrip tests and both common
and historical native validation, including ignored/hidden artifacts.
`just records-check`, `just history-check`, `just validate-schema`, and `just qc`
retain their native contracts. The PR and merge-group validation workflow runs
`tests/test_record_review_contract.py` explicitly and the native tests through QC.

Pages receives the existing metadata API and captures both exact validated YAML
and Markdown bytes once. Both belong to the source-pin inventory. Existing
source checkpoint, curation history, generated-index and status rechecks remain
mandatory. Capture a newly authorized source checkpoint and regenerate Pages
only as part of publication; passing a review never updates a ledger itself.
